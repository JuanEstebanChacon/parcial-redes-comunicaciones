Repositorio: github.com/JuanEstebanChacon/parcial-redes-comunicaciones

Despliegue de cinco servicios orquestados con Docker Compose: un proxy inverso nginx como única puerta de entrada, un CMS Joomla (esta página) sobre PostgreSQL 16, un entorno Jupyter con un cuaderno de análisis precargado y Grafana con fuente de datos y tablero aprovisionados automáticamente. Todo el tráfico que pasa por nginx queda registrado en un log centralizado que analizan tanto Jupyter como Grafana.

1. Cómo encender los contenedores

Requisitos: Docker Desktop (Windows, con WSL2) o Docker Engine con Compose v2, y el puerto 80 libre.

git clone https://github.com/JuanEstebanChacon/parcial-redes-comunicaciones.git
cd parcial-redes-comunicaciones
cp .env.example .env
docker compose up -d

En Windows con Símbolo del sistema (cmd) se usa copy .env.example .env en lugar de cp. La primera ejecución descarga las imágenes, construye la imagen de Jupyter e instala Joomla automáticamente; tarda unos minutos. El sistema está listo cuando docker compose ps muestra los cinco contenedores como (healthy).

2. Puertos

ServicioPuerto interno¿Publicado al host?Cómo se llega
nginx80/tcpSí: 0.0.0.0:80->80/tcphttp://localhost desde el navegador
joomla80/tcpNonginx → joomla:80
database5432/tcpNoJoomla y Grafana → database:5432 por backend_net
jupyter8888/tcpNonginx → jupyter:8888
grafana3000/tcpNonginx → grafana:3000

Base de datos: PostgreSQL escucha en el puerto 5432/tcp, pero ese puerto solo existe dentro de la red backend_net; no está publicado al computador. Joomla se conecta con database:5432: el DNS interno de Docker traduce el nombre database a la IP del contenedor en 172.29.0.0/24. Desde Windows nadie puede conectarse directamente a la base, por seguridad.

Exponer frente a publicar: en la columna PORTS de docker compose ps, 5432/tcp indica un puerto solo interno, mientras que 0.0.0.0:80->80/tcp indica un puerto publicado: el puerto 80 del computador se redirige al 80 del contenedor nginx. Se puede comprobar con docker compose port nginx 80 (responde 0.0.0.0:80) y docker compose port database 5432 (no devuelve ningún puerto).

Decisiones de diseño

  • nginx es el único contenedor con puerto publicado. Los demás solo son alcanzables dentro de las redes de Docker; el único punto de entrada desde el exterior es el proxy, que además registra todo el tráfico.
  • La base de datos vive en una red internal: true. backend_net no tiene salida a internet ni es accesible desde el host; solo entran Joomla y Grafana, que necesitan los datos. Jupyter no tiene acceso a la base.
  • Orden de arranque con healthchecks. Joomla y Grafana esperan a que PostgreSQL esté healthy (pg_isready); nginx espera a que Grafana esté healthy, para no responder con errores 502 durante el arranque.
  • Todo se configura por código. Joomla se autoinstala con variables de entorno, PostgreSQL ejecuta su script de inicio al crearse y Grafana crea su fuente de datos y su tablero por provisioning. No hay pasos manuales.

4. Paso a paso del desarrollo

  1. Estructura del proyecto y Git. Se creó la carpeta parcial-redes-comunicaciones con una subcarpeta por servicio (nginx, database/init, jupyter/notebooks, grafana/provisioning). Git se configuró con core.autocrlf input para conservar los finales de línea de Linux que usan los contenedores.
  2. Variables de entorno. Todas las credenciales se definieron en .env.example. Quien clona el repositorio lo copia a .env y el docker-compose.yml toma los valores de ahí, de modo que ninguna contraseña queda escrita en el compose.
  3. Redes. Se definieron frontend_net (172.28.0.0/24) y backend_net (172.29.0.0/24, internal: true) con subredes fijas para tener un direccionamiento predecible.
  4. PostgreSQL. Servicio database con imagen postgres:16-alpine, healthcheck con pg_isready y volumen db_data para que los datos persistan aunque se borre el contenedor.
  5. Joomla. Autoinstalación por variables de entorno (sitio, usuario administrador y conexión a database), conectado a las dos redes y con depends_on: service_healthy sobre la base.
  6. nginx. Proxy inverso con las rutas /, /jupyter/, /grafana/ y /nginx-health; reenvío de cabeceras Host, X-Real-IP, X-Forwarded-For y X-Forwarded-Proto; soporte de WebSocket, y un formato de log propio (accesos.log) que etiqueta cada petición con el servicio que la atendió. Se verificó con curl que respondiera 200 y 404 y que el log registrara las peticiones.
  7. Jupyter. Imagen propia a partir de minimal-notebook con pandas y matplotlib, servida bajo /jupyter/ (base_url). Se probó el kernel ejecutando una celda: la respuesta llega por WebSocket, lo que confirma que el Upgrade de nginx funciona (en el log aparece el código 101).
  8. Cuaderno precargado. Se escribió analisis_datos.ipynb, que lee el log de nginx con pandas y calcula el total de peticiones, peticiones por servicio, códigos HTTP y tiempo medio de respuesta, con gráficas de barras y de peticiones por minuto. Como la carpeta jupyter/notebooks está montada en el contenedor, el cuaderno queda guardado en el repositorio.
  9. Base de datos lee el log. El script database/init/01_logs_nginx.sql activa la extensión file_fdw y crea la tabla externa nginx_accesos_raw y la vista nginx_accesos, de modo que el log de nginx se consulta con SQL. PostgreSQL ejecuta el script automáticamente la primera vez que se crea la base.
  10. Grafana. Fuente de datos PostgreSQL y tablero de 7 paneles creados por provisioning, servido bajo /grafana/, con acceso anónimo de solo lectura y versión fija (13.2.2). Se le agregó un healthcheck para que nginx espere a que esté listo.
  11. Repositorio. Se agregaron .gitignore (excluye .env y las copias automáticas de Jupyter), .gitattributes (finales de línea LF en cualquier computador) y el README. El proyecto se subió a GitHub con GitHub CLI.
  12. Prueba desde cero. Se clonó el repositorio en otra carpeta y se borraron volúmenes e imagen de Jupyter (docker compose down -v y docker rmi) para simular un computador nuevo. Con solo docker compose up -d se construyó la imagen, se crearon los volúmenes, se ejecutó el script SQL, Joomla se instaló y los cinco contenedores quedaron (healthy).

Problemas encontrados y cómo se resolvieron

  • El script SQL no se ejecutaba: el archivo se había creado en database/ en lugar de database/init/. Se movió a la carpeta correcta y se verificó en los logs la línea running /docker-entrypoint-initdb.d/01_logs_nginx.sql.
  • Errores 502 al arrancar: nginx recibía peticiones antes de que Grafana estuviera listo. Se resolvió con un healthcheck en Grafana y depends_on: service_healthy en nginx.
  • nginx no tomaba la configuración nueva: nginx solo lee su configuración al arrancar, así que tras editar default.conf se recreó el contenedor con docker compose up -d --force-recreate nginx.
  • Finales de línea de Windows: Git para Windows convierte los archivos a CRLF al clonar, lo que podía añadir un carácter invisible a las contraseñas del .env. Se resolvió con .gitattributes forzando LF.

5. Flujo de los datos de monitoreo

  1. nginx registra cada petición en /var/log/nginx/accesos.log con un formato propio separado por |: 
    fecha|ip|servicio|metodo|uri|codigo|bytes|tiempo
2026-09-28T02:20:53+00:00|172.28.0.1|jupyter|GET|/jupyter/api/kernels|200|160|0.002
  2. El log se guarda en el volumen nginx_logs, montado en solo lectura en Jupyter y en PostgreSQL.
  3. Jupyter lo analiza con pandas en el cuaderno analisis_datos.ipynb.
  4. PostgreSQL lo presenta como la vista nginx_accesos mediante file_fdw; el archivo se lee en cada consulta, así que los datos están siempre al día.
  5. Grafana consulta esa vista por backend_net y muestra el tablero "Tráfico del proxy nginx – Parcial 2", que se refresca cada 10 segundos: total de peticiones, errores 4xx/5xx, tiempo de respuesta, peticiones por minuto y servicio, peticiones por servicio, códigos HTTP y las últimas 20 peticiones.

6. Análisis por capas del modelo OSI

Capas 1 y 2 – Física y enlace de datos

No hay cableado físico entre contenedores: la capa física se virtualiza. En Windows, Docker Desktop ejecuta los contenedores en una máquina virtual ligera de WSL2. Allí, cada red del compose es un bridge de Linux, que funciona como un switch virtual. Cada contenedor se conecta al bridge mediante un par veth (un "cable" virtual con un extremo dentro del contenedor, eth0, y el otro en el bridge) y recibe su propia dirección MAC. Los contenedores de una misma red se comunican con tramas Ethernet a través del bridge; los de redes distintas no comparten dominio de difusión.

Capa 3 – Red

  • Direccionamiento: frontend_net = 172.28.0.0/24 y backend_net = 172.29.0.0/24. La dirección .1 de cada subred es la puerta de enlace (el bridge); por eso en el log las peticiones que llegan desde Windows aparecen con origen 172.28.0.1.
  • Aislamiento: backend_net es internal: true; Docker no le crea ruta de salida ni NAT. Se comprobó con docker exec database ping -c 1 -W 2 8.8.8.8, que responde Network unreachable.
  • Resolución de nombres: el DNS interno de Docker (127.0.0.11) traduce el nombre de cada servicio a su IP, por eso la configuración usa nombres: proxy_pass http://joomla:80, JOOMLA_DB_HOST: database, url: database:5432.

Capa 4 – Transporte

Todos los servicios usan TCP: 80 (nginx y Apache de Joomla), 5432 (PostgreSQL), 8888 (Jupyter) y 3000 (Grafana). Solo el puerto 80 de nginx está publicado: Docker reenvía las conexiones que llegan al puerto 80 del host hacia el puerto 80 del contenedor nginx (redirección de puertos con NAT). Los demás solo están expuestos dentro de las redes de Docker. nginx termina la conexión TCP del cliente y abre una conexión nueva hacia el servicio de destino; el cliente nunca se conecta directamente con Joomla, Jupyter o Grafana.

Capas 5 y 6 – Sesión y presentación

  • Sesión: Jupyter (canal del kernel) y Grafana (actualizaciones en vivo) mantienen sesiones persistentes por WebSocket; nginx las conserva abiertas con proxy_read_timeout 86400. Joomla y Grafana gestionan además sesiones de usuario con cookies.
  • Presentación: los datos viajan como HTML, JSON y texto plano. El despliegue usa HTTP sin cifrar por ser un laboratorio local; en producción se añadiría TLS en nginx (HTTPS, puerto 443).

Capa 7 – Aplicación

RutaDestino
/joomla:80
/jupyter/jupyter:8888 (Jupyter con base_url=/jupyter/)
/grafana/grafana:3000 (Grafana con serve_from_sub_path)
/nginx-healthRespuesta directa de nginx (200 ok)

Cabeceras que el proxy reenvía, porque de otro modo los servicios solo verían la IP y el nombre de nginx: Host (dominio y puerto que escribió el usuario), X-Real-IP y X-Forwarded-For (IP real del cliente), X-Forwarded-Proto (protocolo original), y Upgrade y Connection, necesarias para el HTTP Upgrade a WebSocket. Estas dos últimas son hop-by-hop y un proxy no las reenvía por defecto; el bloque map $http_upgrade $connection_upgrade decide el valor de Connection.
